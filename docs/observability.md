# Observability

Metrics, logs, dashboards and alerts for Cardwar. Design: `docs/superpowers/specs/2026-10-12-mvp-design.md` §8;
plan: `docs/superpowers/plans/2026-10-12-mvp1-observability.md`. The pattern is the one submissions-checker uses.

## How it fits together

```
app ──/actuator/prometheus──┐
                            ├─ Alloy ── remote_write ──> Prometheus  (Grafana Cloud in prod, local container on a laptop)
every container's stdout ───┘        └─ push ─────────> Loki        (Grafana Cloud in prod, local container on a laptop)
```

- The app exposes `/actuator/prometheus` on the compose network only; nginx answers 404 for it.
- **Grafana Alloy** (`observability/alloy/config.alloy`, compose service `alloy`, profile `observability`) scrapes the
  app every 30 s as `job="cardwar"` and tails every container of the compose project through a read-only Docker
  socket. It pushes outbound, so the server publishes nothing new. Every series carries `env` (`prod` / `local`).
- Dashboards and alert rules are generated by `observability/grafana/build.mjs` into committed files and pushed to
  Grafana Cloud by `observability/grafana/push.mjs`. The local Grafana loads the very same files.

## What is measured

| Dashboard | Question | Source |
|---|---|---|
| **Cardwar — Technical** (`cardwar-technical`) | Is the service healthy? | up, HTTP rate by route template and status class, p95 latency, 5xx ratio, JVM heap, process CPU, Hikari connections, SSE streams open, Telegram bot updates by outcome |
| **Cardwar — Business** (`cardwar-business`) | Do people play? | sign-ins by method, duels started by mode, finished by result and reason, moves by type and outcome, invites by event, invite conversion (accepted / created) |
| **Cardwar — Logs** (`cardwar-logs`) | What happened to this request? | log volume by level, error lines by service, every error, the app log filtered by `requestId` and free text |

Business counters come from `cardwar.metrics.GameMetrics`: `cardwar_signins_total{method}`,
`cardwar_duels_started_total{mode}`, `cardwar_duels_finished_total{result,reason}`, `cardwar_moves_total{type,outcome}`,
`cardwar_invites_total{event}`, `cardwar_bot_updates_total{outcome}` and the gauge `cardwar_sse_streams_open`. The
invite conversion panel assumes the `event` values `created` and `accepted`.

The HTTP p95 panels read the `http.server.requests` percentile histogram, enabled in `application.yml`
(`management.metrics.distribution.percentiles-histogram`). Counters with tags appear on first use, so
`cardwar_bot_updates_total` has no series until the bot has received an update.

### Alerts (`observability/grafana/alerting/alert-rules.yaml`)

| Rule | Fires when | Why |
|---|---|---|
| ServiceDown | `max(up{job="cardwar"}) < 1` for 3 min; no data at all also fires | the app or Alloy is gone |
| HighErrorRate | 5xx above 5 % of requests over 10 min, with more than 20 requests, for 5 min | players see errors |
| BotUpdatesFailing | `cardwar_bot_updates_total{outcome="failed"}` rising for 10 min | invites and the Play button stop working |

They notify the Telegram contact point `cardwar-telegram` through a notification-policy route matching `app=cardwar`.

### Series budget: no ids as labels

Grafana Cloud's free tier allows 10k active series, shared with other projects on the same stack. Cardwar aims for
under 600. Label values therefore come from closed enums only (method, mode, result, reason, move type, outcome,
event); a player id, duel id, invite id or username never becomes a label. HTTP is labelled by route template
(`/api/v1/duels/{id}`), never the raw path. Logs get four labels only (`app`, `env`, `service`, `level`); ids stay in
the JSON line and are read at query time with `| json`. Before adding a metric, count its label combinations.

## Logs

The app logs Spring Boot's logstash JSON in the prod profile; MDC fields such as `requestId` are top-level keys. Alloy
labels each line with `app="cardwar"`, `env`, `service` (the compose service) and `level` (`INFO`, `WARN`, `ERROR`,
from the JSON). Lines that are not JSON (Postgres, Redis) pass through without a level.

Find everything about one request: take `X-Request-Id` from the response, paste it into the `requestId` box on the
Logs dashboard. In Explore:

```
{app="cardwar", service="app"} | json | requestId="<id>"
{app="cardwar", level="ERROR"}
sum by (level) (count_over_time({app="cardwar"} [5m]))
```

## Local harness

```
make up                 # the app stack, as usual
make observability-up   # Alloy + throwaway Prometheus, Loki, Grafana
open http://localhost:3000   # anonymous admin; dashboards in the "Cardwar" folder
make alloy-logs         # rejected pushes or empty discovery show here
make observability-down
```

`observability-up` loads `docker-compose.observability-local.yml` on top of the base file. It points Alloy at the
local Prometheus (`http://prometheus:9090/api/v1/write`) and Loki (`http://loki:3100/loki/api/v1/push`) with dummy
credentials and publishes 3000 (Grafana), 9090 (Prometheus), 3100 (Loki) and 12345 (Alloy UI) on loopback. Never load
that file on a server. The target passes the resolved compose project name to Alloy as `CARDWAR_COMPOSE_PROJECT`;
without it a worktree checkout would filter on the wrong label and tail nothing.

## Production

On the server, add to `/opt/cardwar/.env` (mode 600; never commit or paste these anywhere):

```
COMPOSE_PROFILES=observability
CARDWAR_ENV=prod
GRAFANA_CLOUD_PROM_URL=https://prometheus-prod-XX.grafana.net/api/prom/push
GRAFANA_CLOUD_PROM_USER=<numeric Prometheus instance id>
GRAFANA_CLOUD_PROM_TOKEN=<access-policy token, metrics:write>
GRAFANA_CLOUD_LOKI_URL=https://logs-prod-XX.grafana.net/loki/api/v1/push
GRAFANA_CLOUD_LOKI_USER=<numeric Loki user id>
GRAFANA_CLOUD_LOKI_TOKEN=<access-policy token, logs:write>
```

Then deploy as usual (`git pull && make up`). `make up` passes every profile in `COMPOSE_PROFILES` on to compose, so
the `alloy` service (128 MB limit, WAL in the `alloy-data` volume) starts beside the app. Check it with `make ps` and
`docker logs cardwar-alloy`: no `401`/`403` means the tokens work, and the series appear under `job="cardwar"`,
`env="prod"` in Grafana Cloud within a minute. The local Prometheus, Loki and Grafana are in the separate
`observability-local` profile and never run there.

## Pushing dashboards and alerts

From a workstation with these in the local `.env`:

```
GRAFANA_URL=https://<stack>.grafana.net
GRAFANA_API_TOKEN=<service-account token, Editor>
TELEGRAM_BOT_TOKEN=<the bot that sends alerts>
GRAFANA_ALERT_CHAT_ID=<chat id that receives them>
```

```
make dashboards-json   # regenerate after editing build.mjs; commit the output
make dashboards        # folder "Cardwar" (uid cardwar) + the three dashboards, overwritten in place
make alerting          # contact point cardwar-telegram, its policy route, rule group cardwar
```

`push.mjs` touches only cardwar-owned objects and sends `X-Disable-Provenance: true`, so pushed objects stay editable
in the UI. It never prints a token.

## Changing a dashboard or adding a metric

1. Edit `observability/grafana/build.mjs` (never the generated JSON/YAML), then `make dashboards-json`.
2. A new metric name goes into `observability/grafana/exported-metrics.txt` once the app really exports it.
3. `node --test observability/grafana/build.test.mjs` (also run in CI) checks that the committed files match the
   generator, that every PromQL metric is in the exported list, and that every selector filters on `job="cardwar"`.
